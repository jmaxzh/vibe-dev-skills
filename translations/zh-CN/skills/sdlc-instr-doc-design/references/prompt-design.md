# 提示词设计指导原则

设计、撰写、修改或审查约束模型行为的指令、提示词、技能及文档中的模型执行规则时，使用以下原则，并遵循主技能的[共同表达规则](../SKILL.zh-CN.md#共同表达规则)。

## 一、通用原则

1. 最小充分：仅保留对任务执行或结果有实际作用的指令，避免重复、套话及无必要的约束。
2. 明确可执行：使用简洁、明确的指令句；写清执行任务所需的主体、对象、条件、动作及结果要求。
3. 避免重复通识：不重复说明模型已具备的通用知识和基础能力，但保留任务所需的具体约束。
4. 按需选用维度：使用通用维度检查所有提示词；场景维度仅在符合启用条件时应用。
5. 边界清晰：区分指令与数据；仅按任务需要规定证据要求、操作权限及不确定性的处理方式。
6. 结果导向：明确预期结果、必要约束和完成标准。
7. Context, not Control：提供相关背景、事实、约束原因和取舍依据，支持自主判断。由模型选择方法，仅在任务依赖关系、接口要求或已识别风险需要时规定具体步骤。

理念参考：[奈飞：Context, not Control](https://www.jobs.netflix.com/culture)；[字节跳动：Context over Control](https://www.bytedance.com/about)。

## 二、通用设计维度

使用这些维度检查提示词是否提供了充分指导，不要求为每个维度单独编写指令；任务或上下文已明确的要求无需重复补充。

| 设计维度 | 推荐方法 | 不推荐做法 | 原因与适用条件 |
| --- | --- | --- | --- |
| 任务定义 | 明确目标、对象、结果和完成条件，提供判断所需的上下文与取舍依据 | 目标笼统、对象不明、缺少决策上下文或加入无关背景 | 支持有依据的方法选择，并使完成要求清晰 |
| 指令明确性 | 使用简洁、可执行的指令，写清必要的主体、对象、条件、动作和结果 | 模糊表达、缺少关键条件或提出无法指导行动的要求 | 减少歧义与不必要的推断 |
| 指令长度 | 使用最小充分指令，保留实际影响任务执行或结果的内容 | 重复同义规则、重复说明模型已具备的通用知识与基础能力、堆叠泛泛告诫和套话 | 减少冗余及过度约束，同时保留任务所需的具体规则 |
| 输入组织 | 明确区分任务指令与待处理内容；必要时使用字段或分隔符 | 混淆指令和数据，或对简单输入强加不必要的结构 | 明确处理对象，避免不必要的结构 |
| 输出约束 | 明确结果必须包含的内容；仅在需要时规定格式、长度及结构 | 缺少影响结果使用的输出要求，或增加不影响实际使用的格式限制 | 保证结果满足任务需求，避免无必要的输出限制 |

## 三、分场景启用的设计维度

仅在启用场景成立，且现有提示词尚未充分表达相应要求时，增加必要指令。

| 设计维度 | 启用场景 | 推荐方法 | 不推荐做法 |
| --- | --- | --- | --- |
| 任务分解 | 依赖关系、接口要求或已识别风险需要划分阶段 | 明确必要阶段及其目的、依赖和结果；其他方法由模型选择 | 无具体需要却规定执行顺序 |
| 指令层级 | 存在不同来源、优先级或用途的指令和资料 | 明确各类指令和资料的作用、优先级及适用范围 | 混淆指令与资料，或让低优先级内容覆盖高优先级规则 |
| 推理引导 | 任务要求特定分析方法、论证框架或验证过程 | 规定必要的分析角度、方法和可验证结果 | 普遍要求逐步思考或展示完整内部思维链 |
| 少样本示例（Few-shot） | 文字规则不足以明确分类边界、判断标准或输出形式 | 提供少量具有代表性且与规则一致的正例、反例或边界例；明确示例用于说明的要求 | 堆叠重复、无关或相互矛盾的示例，或让示例中的偶然细节成为额外约束 |
| 证据使用 | 任务需要依据指定资料作答、核查事实或提供引用 | 明确证据范围、引用要求及来源冲突的处理方式 | 无证据补充事实、伪造引用或忽略来源冲突 |
| 异常与不确定性处理 | 信息缺失、输入无效或来源冲突可能影响结果 | 明确如何处理相关异常，以及信息不确定时如何回应 | 无条件要求确定答案，或添加缺乏具体依据的异常规则 |
| 工具使用指令 | 任务允许或需要使用外部工具 | 明确工具调用条件、用途、结果使用规则及必要确认条件 | 虚构工具执行结果、猜测必要参数或扩大操作权限 |
| 模板化与参数化 | 提示词需要复用、批量处理或动态填充内容 | 使用含义明确的变量，区分固定指令与可变数据 | 使用含义不明的占位符或随意拼接指令与数据 |
| 角色与受众设定 | 专业职责、目标受众或表达语域会实质影响结果 | 明确必要的角色、职责、受众及表达要求 | 无实际作用的专家角色扮演或冗长身份描述 |

## 四、指令增删与维护原则

以下原则用于新增、修改、压缩或删除提示词内容。

| 维护操作 | 指导原则 |
| --- | --- |
| 新增指令 | 仅在存在明确任务需求、可识别风险或实际问题时添加；优先补充缺失的条件与约束 |
| 修改指令 | 消除歧义、矛盾和执行边界不清的问题；用决策上下文与结果要求替代不必要的过程控制，不无故扩大范围 |
| 压缩指令 | 删除重复、套话、泛泛告诫及无实际作用的通识性说明，保留必要信息 |
| 删除指令 | 删除不影响任务执行及预期结果的内容；不得仅因模型已掌握相关知识而删除必要约束 |
| 合并指令 | 合并适用条件和预期行为一致的重复要求；保留具有不同条件、对象或作用的独立规则 |
| 保留指令 | 对结果正确性、证据边界、操作权限或必要异常处理具有明确作用的指令应予保留 |

## 五、最终检查

- 任务目标、处理对象和预期结果是否明确？
- 是否存在模糊、重复、空泛或无必要的指令？
- 是否重复强调模型已具备的通用知识或基础能力？
- 是否保留了任务必需的条件、约束及行为边界？
- 是否只启用了实际需要的场景维度？
- 指令、数据及示例的边界是否清楚？
- 示例是否具有代表性、与规则一致，且未将偶然细节变成额外约束？
- 是否有足够的相关上下文支持方法选择和取舍判断，同时避免无关背景？
- 每项规定的步骤、格式、结构或角色是否服务于具体任务需要，还是可以改用上下文与结果要求？

核心原则：以最小充分指令为基础，提供与决策相关的上下文，明确任务与必要边界，按实际场景补充要求，不重复模型通用能力，不为形式完整而增加指令。
